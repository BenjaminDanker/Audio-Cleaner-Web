# What is worth running on the GPU (2026-10-17)

Question: the GTX 960 (4 GB, Maxwell sm_52, driver 580) only runs Parakeet. Which other stages gain from it, by how much,
and what has to be true so that two things do not collide on a 4 GB card? Measured on the production box with
onnxruntime-gpu 1.19.2 (the GPU venv; the last build with sm_52 kernels, CUDA 12.9 wheels, cuDNN 9.7.1), against the
CPU path of the production venv (onnxruntime 1.31). `tools/bench_gpu.py` is the harness (wall time, process CPU time,
the card's peak memory from `nvidia-smi`, SNR against the CPU output). Raw outputs and the other scripts were kept in the
session scratchpad (`gpu/`).

**Read the CPU columns with care.** The box was never idle during these runs (load average 9 to 14 from other sessions'
benchmarks, Minecraft); the CPU runs were pinned with `taskset` to four physical cores and `nice 10`, but SMT siblings and
the memory system were shared, so CPU seconds are inflated (DPDFNet batched: 1.1 cpu-s/s here against 0.5 to 0.6 in
`heavy-2026-10.md`, Parakeet 0.61 against 0.34). Where the earlier quieter figure exists it is given next to it. GPU runs
are less affected (their CPU share is small) but the Python/ffmpeg side of Parakeet is: the same 150 s ran in 5.6 s and in
13.5 s depending on what else ran. Another session also used the card briefly while these ran (a 0.6 GB peak showed up once in a CPU-only run), so single GPU timings can be off by that. Speed is audio seconds per wall second, "cores" is process CPU time over wall time.

## 1. DPDFNet-8 (the heavy noise remover): worth it, with limits

The batch-1 model is hopeless on the card (35 ms a frame, 3.5 s of wall time per second of audio). The batched model
(`dpdfnet8_48khz_hr_batch.onnx`, `tools/export_dpdfnet_batch.py`) is what makes it work, with three things on top:

* **CUDA graphs.** One 10 ms frame is about 600 small kernels; launched one by one a call costs 18 to 35 ms at any batch
  size, as one graph replay it costs 8.7 ms for one row and 38 ms for 64 (table below). The state of every row stays on the
  card (two buffers per size, the graph reads one and writes the other); only the 3.8 KB spec goes up and comes back per row.
  A call is padded to the next of 13 sizes (2 to 64 rows), each its own graph (about 90 MB, made when first used).
* **Rows.** A row is one segment of the file as the CPU path cuts it (60 s segments, 2 s warm-up, same crossfades): the
  segmentation is the same, so the output is the same. The card is latency bound, so all segments of the file go in one call:

  | rows per call | 1-4 | 8 | 12 | 16 | 32 | 64 |
  |---|---|---|---|---|---|---|
  | ms per 10 ms frame | 8.7-9.6 | 11.0 | 12.8 | 14.8 | 23.2 | 38.4 |
  | ms per row-frame | 8.7-2.4 | 1.37 | 1.06 | 0.93 | 0.73 | 0.60 |

  So wall time per file is about (longest segment + warm-up) x (1.2 at 10 rows, 1.8 at 20, 3.8 at 64), almost
  independent of the file length until it has more than ~16 segments: a 485 s file (10 rows) takes 78 s, a 32 min file
  (33 rows) 177 s (11x). **Short files gain little**: 150 s mono is cut into 4 segments of 37 s by the same rule as on
  the CPU (`_plan`), which takes 40 s on the card against 47 s on four loaded cores. Cutting short files into more
  segments would make the card much faster but changes the output (20 to 26 dB SNR against a sequential pass, see
  `heavy-2026-10.md`), so it was not done; the CPU is freed all the same (0.15 cores against 3.7).
* **Host thread asleep.** By default the host thread spins while it waits for the card: 39 CPU-s for 150 s of audio.
  `cudaSetDeviceFlags(cudaDeviceScheduleBlockingSync)` before the first session (`acw_common.gpu.prepare_cuda`) makes it
  sleep: 5.3 CPU-s, wall time +3 %.

Tried and dropped: two sessions in two threads (two streams) do not overlap (16 % more rows per second in total: the card
is the limit, 90 % busy); a second group of rows cannot use the idle half of a small call.

Memory: 265 to 316 MB for the whole card (context ~170 MB, state and graphs per size). Quality: the output equals the CPU
output (SNR 124 to 127 dB, onnxruntime 1.19.2 against 1.31, different GEMM kernels), also through the sandboxed runner
(`tests/test_gpu.py`). Limits: it needs the **batched model file** in `models/dpdfnet` (it is only "local optional" in
`deploy/models.lock`; production has only the batch-1 file today) and onnxruntime-gpu 1.19.2 with CUDA 12 / cuDNN 9.7.

## 2. Sidon voice rebuild: the biggest win

Windowed w2v-BERT features (16 s windows) and DAC decoder blocks are plain ONNX graphs with dynamic shapes; no graph
capture, no padding. 7.4x real time against 0.74-1.1x on four CPU cores and 4.6 cpu-s/s (0.017 on the card): a one-hour
file takes 8 minutes instead of 1 to 1.4 hours and does not occupy four cores and 4.5 GB of RAM for it. Output equals the
CPU's (SNR 95.6 dB; the difference is float round-off of the two onnxruntime builds).

Memory is the issue. onnxruntime's arena rounds every growth up to a power of two: with the default the card peaks at
3.7 GB, with `arena_extend_strategy=kSameAsRequested` at **2.6 GB** with the same speed. 1.0 GB per session as
`gpu_mem_limit` is too little, 1.5 GB works; the two sessions (features 400 MB of weights, decoder 105 MB) and their
activations (a 10 s decoder block or a 16 s feature window, ~0.7 GB) are what is held. Two calls in flight (as the CPU
pool does) add 1 GB and no speed (7 % at most), so the card runs one call at a time. The int8 feature extractor is a CPU
trick and is not used on the card.

## 3. AP-BWE: faster, but the CPU is the limit

The generator is a convolution stack: 11x real time on the card against 1.7x on four loaded CPU cores. The rest is numpy
(resampling, STFT, ISTFT per 6 s block: 2.9 of the 3.3 CPU-s of a 60 s run), so the card is idle 70 % of the time and the
run needs 0.7 cores; it frees ~2 cores and runs in a seventh of the time. Only phone-quality recordings get it. 359 MB.
Output equals the CPU's (SNR 125 dB).

## 4. Whisper: nothing runs

* The pinned CTranslate2 4.8.2 wheel reports `float32` as the only compute type on this card and fails with
  `cudaErrorInvalidDevice` on the first call: it has no sm_52 code (as `asr.md` found).
* CTranslate2 3.24.0 (CUDA 11.2 build, cuBLAS 11 / cuDNN 8 wheels, faster-whisper 0.10.1, a separate throw-away venv) runs
  on sm_52, **float32 only** (float16 and int8 need sm_53 / sm_61). Whisper small works (11.6x, WER 9.24 % on the 150 s,
  2.4 GB). **Large-v3-turbo in fp32 is 3.2 GB of weights**: the model loads (3.37 GB) and dies in the encoder at 3.9 GB of
  the 4. Even if it fitted, a second CUDA runtime (11.x) in the GPU venv and an old faster-whisper would be needed; the
  fp32 turbo would not share the card with anything. Not worth building: Whisper is for the languages Parakeet does not
  cover, it stays on the CPU (int8, `heavy-2026-10.md` section 7 for its tuning).
* Language detection: base on the card is 0.14 s plus 0.9 s of load (0.5 GB) against 2.7-3.1 CPU-s on one thread, small
  0.49 s plus 1.7 s (2.2 GB) against 9.5-12 s. It saves 2.7 CPU-s per job with an unknown language, and costs the second
  CUDA runtime above and a CUDA context in a process that otherwise has none. Not done.

## 5. Parakeet (what runs there today)

27x with 4.4 CPU-s for 150 s on a quiet box (11x with 12.5 CPU-s while the CPU was loaded: the VAD, the mel front end and
the TDT decoding loop are CPU and Python, 80-90 % of a core), 3.2 GB at the peak. Two changes made here, with the same
transcript (segments, text and timestamps identical on 150 s and 695 s, WER 5.28 % / 3.04 %):

* The Silero VAD now runs on one CPU thread like on the CPU path, instead of on the card with a default thread pool
  (150 s: 8.8 CPU-s and 9.7 s against 4.9 CPU-s and 5.9 s).
* The arena grows by what is asked: 2.8 GB for 150 s and 3.2 GB for 11.6 min instead of 3.4-3.6 GB.

The weights are 2.4 GB, so nothing else fits next to it. After `transcribe_parakeet` returns the card is back at its idle
78-103 MB, so a job can use another model afterwards.

## 6. The rest

* **Live captions** (sherpa-onnx streaming transducer, int8 encoder, 0.2-0.3 core a stream): no. A chunk is one small
  call; the card's floor for one call of the tiny DPDFNet model is 8.7 ms with every kernel in a graph and 18-35 ms
  without, more than the CPU spends on a chunk, and the int8 file has the CUDA provider has few kernels for. Not measured on the real model.
* **Live noise removal** (one 10 ms frame per call): cannot even run in real time on the card (8.7 ms for one stream,
  11 ms for 8, more for more), and the host thread would be pinned.
* **DeepFilterNet3** is libDF/tract (CPU only). The clarity chain, resampling and decoding are numpy / ffmpeg.
* Larger models from the earlier research (`denoise.md`: MossFormerGAN at 3.6 GB / 1.0x real time, Resemble) were rejected on
  quality, not speed.

## What was implemented

* `acw_common.dpdfnet.denoise_array(device="cuda")`, `restore.restore(device=...)`, `bwe.extend(device=...)`,
  `pipeline.CleanOptions(device=, heavy_device=)`; `acw_common.gpu.prepare_cuda`. **No CPU fallback**: when CUDA cannot be
  used (no card, libraries missing, a session that did not get the CUDA provider, the batched DPDFNet file missing) they
  raise and the job fails with the usual "not charged" message. Where a GPU job is allowed to use the CPU it is the worker's
  explicit choice: `heavy_device` is "cpu" in the GPU worker when the batched file is not installed.
* The GPU worker (`worker/main.py`) takes: local transcription (as before), voice-rebuild jobs, and heavy / auto noise
  jobs when the batched file is installed; AP-BWE and DPDFNet run on the card inside them. It runs one job at a time.
  CPU workers leave these jobs to an idle GPU worker as they did for transcription; the voice rebuild (hours of four cores
  on the CPU) also waits while the GPU worker is busy, as long as it is up (`data/gpu-worker-alive`); everything else a
  busy GPU worker leaves is taken by the CPU workers as before. Echo-removal jobs stay with the CPU workers (no echo canceller
  in the GPU venv), light cleaning and Whisper have no GPU path.
* Tests: `server/tests/test_gpu_routing.py` (routing, markers), `common/tests/test_dpdfnet.py` (the GPU path with the batched
  CPU model dressed as the card: one group, grouping by rows, same output), `test_noise_profile.py` (device reaches every
  stage), `test_gpu.py` ("cuda" raises without CUDA; with `ACW_TEST_GPU=1` and the GPU venv: DPDFNet, AP-BWE and Sidon
  against the CPU path, graph reuse and sizes). The sandboxed runner was run end to end on the card (Parakeet then DPDFNet,
  Parakeet then Sidon, light cleaning with AP-BWE): same outputs as the CPU run, 124 dB SNR on the audio.

## Numbers for the resource broker

One GPU job at a time. The workloads are compute bound on the card (DPDFNet 90 % busy, Sidon 85 %, two DPDFNet streams
together only 16 % faster than one), so sharing the card buys no throughput even where the memory would fit; memory alone
allows DPDFNet or AP-BWE next to Sidon (2.6 + 0.4 GB) and DPDFNet next to Parakeet (3.2 + 0.3 GB, too tight to rely on).
Seconds are per minute of audio and per channel that is processed (a stereo file whose channels differ is two; DPDFNet's
stereo rows share a call, so its time grows with the rows only slowly). Host RAM of the runner: 0.8-1.6 GB; host
CPU 0.1-0.9 core; model load and CUDA start: 4-5 s (DPDFNet), 5-7 s (Sidon), 1-1.4 s (AP-BWE), 3-5 s (Parakeet).

| workload | GPU MB (peak) | wall seconds per audio minute | cores | exclusive? |
|---|---|---|---|---|
| Parakeet v2/v3 transcription | 3300 | 1.4-2.3 quiet, 5.5 with the CPU loaded | 0.8-0.9 | exclusive |
| DPDFNet-8 heavy noise removal | 300 | 5.5 on a 32 min file, 9.7 at 8 min, 16 at 2.5 min (a file has few rows, and a call costs the same for 1 to 8) | 0.1 | exclusive in practice |
| Sidon voice rebuild | 2600 | 8.2 (7.4x) | 0.13 | exclusive |
| AP-BWE highs restoration | 360 | 4.4-5.4 | 0.7 | exclusive in practice |
| Whisper / language detection / live | not on the card | | | |

Together in one job they run one after the other and give the card back in between (Parakeet leaves 78-103 MB).
The broker's `gpu` branch (`min(mem, JOB_MEM + 1 GB)` of host memory) still holds: the runner's RSS on the card was 0.8-1.5 GB
(Parakeet then Sidon in one job: peak RSS 1.9 GB including the mapped model files).

## Not done / open

* The batched DPDFNet file has to be installed on the machine (`models/dpdfnet/`) before heavy / auto jobs go to the card;
  until then they stay on the CPU workers (the GPU worker still takes Parakeet and rebuild jobs).
* Parakeet still asks for `CPUExecutionProvider` after CUDA in its provider list and does not check that the session got
  the card. Making it raise like the other three needs a look inside onnx-asr (private attributes); not done.
* No CPU number here comes from a quiet machine; rerun `tools/bench_gpu.py ... --device cpu` on an idle box for the CPU side
  of the table (the GPU side moves little with load, except Parakeet).
* Short files (under ~5 minutes) gain little speed from DPDFNet on the card; a GPU-specific segmentation (many short
  segments) would, at the cost of a different (equally valid, 20-26 dB SNR from the CPU path's) output.
