# CPU and memory savings in the heavy models (2026-10-17)

Follow-up to the 2026-10-16 audits. Everything here was measured on the production box (Ryzen 1700X, 8 cores / 16 threads,
shared with other work, `nice 10`, pinned with `taskset`; the machine was never idle, so single numbers carry about +-5 %).
"cpu-s/s" is process CPU seconds per second of audio. Output checks compare against the code before the change, same input.
Scripts and raw outputs are in the session scratchpad (`h26/`); `tools/export_dpdfnet_batch.py` is the only new tool.

| # | Change | Before -> after | Output check |
|---|--------|-----------------|--------------|
| 1 | Parakeet on the CPU: VAD batch 1, VAD on 1 thread, 2 encoder threads, no ORT prepacking | 0.44-0.50 -> 0.34 cpu-s/s (-23 to -32 %); private memory peak 2.8 GB -> 0.27 GB | WER 5.28 % both; 1 punctuation mark and one 80 ms word boundary differ in 298 words |
| 2 | Language detection: Whisper base, small only when base is < 60 % sure | 9.5 -> 2.7 cpu-s per detection (-72 %) | 109/120 correct, same total as small alone, on hard material (see 2); base alone: 105 |
| 3 | Sidon: worker pool of single-thread session calls, 10 s decoder blocks with 10 frames of context, no whole-file temporaries | 5.1-5.2 -> 4.8-5.0 cpu-s/s on 2 cores (-3 to -7 %), 4 physical cores -10 to -13 %; wall -13 to -17 %; peak RAM 2.3 GB -> 4.0 GB; `_side_db` on 30 min stereo 2.0 GB -> 56 MB | bit-identical (max abs diff 0) |
| 4 | AP-BWE: context 2560, blocks of 6 s, no spinning | 0.843 -> 0.833 cpu-s/s (-1 %), peak RAM +0.15 GB | bit-identical |
| 5 | DeepFilterNet: model once per thread | not done (see 5) | - |
| 6 | DPDFNet-8: batched model, several segments per call | 0.76-1.0 -> 0.51-0.62 cpu-s/s on long files (-33 to -38 %), wall -22 to -28 % | bit-identical (max abs diff 0 on 8 min of speech, also with `atten_lim_db` 12) |
| 7 | Whisper turbo: BatchedInferencePipeline | not adopted (see 7) | - |

## 1. Parakeet on the CPU

150 s of LibriSpeech (`libri/stream16k.wav`, 18 VAD pieces), `transcribe_parakeet` as called by the runner with `threads=4`:

| setting | threads | cpu-s per audio s | WER | private memory peak |
|---|---|---|---|---|
| before (VAD batch 8, VAD default threads, 4 encoder threads) | 4 | 0.443, 0.501 | 5.28 % | 2.80 GB |
| VAD batch 1, VAD 1 thread, 4 encoder threads | 4 | 0.365, 0.433 | 5.28 % | 2.30 GB |
| same, 2 encoder threads | 2 | 0.310, 0.317 | 5.28 % | ~2.3 GB |
| same, 1 encoder thread | 1 | 0.294 (wall 44 s instead of 26 s) | 5.28 % | ~2.3 GB |
| **2 encoder threads + `session.disable_prepacking=1` (shipped)** | 2 | 0.341, 0.349 | 5.28 % | **0.27 GB** |

The encoder gains little from more than two threads; one thread would save another 6 % at +70 % wall time, so two it is.
Prepacking off costs 9 % CPU and turns the 2.4 GB of weights into the model file's page cache: shared by concurrent jobs,
evictable, not charged as private memory (peak RSS including the mapped file is 2.6 GB either way; two concurrent jobs
need about 3.0 GB instead of 6.8 GB). Net against the old setting: -23 to -32 % CPU and 2.5 GB less private memory.
The CUDA path is untouched (its VAD and batch size are as before).
Transcript differences against the old setting: segment 7 ends in "!" instead of "." and one word boundary moves by one
80 ms frame; batch 1 avoids the padding of the old batch of 8, so these differences come from the old side.

## 2. Language detection

`detect_language` takes base first and asks small only when base's probability is below 0.6 (`LANGUAGE_CONFIDENCE`).
Test set, 12 languages (FLEURS: en de fr es ru ja ar hi zh pt tr ko), faster-whisper int8, 1 thread, 30 s of speech:

| condition (12 languages each) | base | small | base, small when < 0.6 |
|---|---|---|---|
| speech with synthetic music, 10 / 5 / 0 dB | 36/36 | 36/36 | 36/36 |
| 4 other-language voices as babble, 5 dB | 11 | 10 | 10 |
| same, 0 dB | 7 | 9 | 8 |
| telephone band (300-3400 Hz, 8 bit noise) | 12 | 12 | 12 |
| one utterance of 1 / 2 / 3 / 5 s | 8 / 9 / 10 / 12 | 8 / 10 / 12 / 12 | 9 / 10 / 12 / 12 |
| **all 120 cases above** | 105 | 109 | **109** |

Two-language recordings (first 20 s one language, last 10 s another; and the reverse) were run too; the detector hears the
first 30 s of speech and the "right" answer is ambiguous, so they are not in the 120 (against the language of the larger
part: base 20/24, small 17/24, base with the rule 19/24). Base on its own is worse than small on 2-3 s clips and on 0 dB babble, so it is not used
alone; with the 0.6 rule base never was confidently wrong (no wrong answer with p >= 0.8 among the 120), the total equals
small's (case by case it differs in two places, one worse and one better), and the fallback is taken in 17 of the 120
deliberately hard cases; the audit's clean and 5 dB-noise read speech (96 cases) was 96/96 for base alone. CPU per detection including the
model load, 30 s of speech: base 2.7, small 9.5 (the rule costs 12.2 when it falls back). The synthetic music is a
chord-and-drum synthesiser, not a recording; no real music was available on the box. Subtitles keep their models.
`runner.py` uses small alone while `models/whisper/base` is not installed; `health.REQUIRED_MODELS` now lists it.
Base is pinned in `deploy/models.lock` (Systran/faster-whisper-base commit ebe41f7, 145 MB, same four files as small).

## 3. Sidon (`restore.py`)

All variants below produced exactly the same samples as the old code (checked on 20, 40, 60 and 150 s of speech):
decoder blocks 6 s / 12 frames vs 10 s / 10 frames, one four-thread session vs a pool of single-thread calls,
arena on/off, graph optimisation basic/extended.

* **Pool.** Windows and decoder blocks are independent, so they run as calls to shared single-thread sessions on a pool of
  `threads` workers (at most 4, `_MAX_WORKERS`). The dither is drawn in window order in the caller, so it is reproducible.
  4 physical cores (taskset 0-3, 30 s and 60 s clips): old 2.59-3.3, pool 2.27-2.36 cpu-s/s; wall -6 % on 60 s.
  On the two physical cores (4 hardware threads) the pinning of these benchmarks allows, 150 s: old 5.07 / 5.18,
  pool 4.98 / 4.82 cpu-s/s, wall 284 / 287 s -> 247 / 239 s. The audit's 12-17 % holds when the workers have cores of
  their own and shrinks to 3-7 % when they share them.
* **Memory cost.** Every concurrent call keeps its activations (feature window of 16 s: ~0.7 GB, decoder block: ~50 MB per
  second of block, both kept by onnxruntime's arena). Peak RSS: 2.2-2.3 GB before, 4.0-4.2 GB now with four workers;
  two windows at most are in flight (`_FE_AHEAD`) because the feature extractor is only a fifth of the work. 3 workers:
  2.9 GB, 2 workers: 2.7 GB (but +80 % wall). `JOB_MEM_REBUILD` is now 4.5 GB. If that is too much on a given host,
  lower `_MAX_WORKERS`.
* **Decoder blocks.** 6 s -> 15 s / 10 frames saves about 2 % CPU (the audit's 7 % was the decoder alone), and costs 0.4 GB
  per concurrent block; 10 s keeps most of it (block overhead 8 % -> 4 %) for half the memory, so 10 s is used.
* **Arena off** (`enable_cpu_mem_arena=False`) saves 0.3 GB at one worker but costs +28 % CPU (every activation is freshly
  allocated and page-faulted): rejected. **Graph optimisation**: only `DISABLE_ALL` halves the 1.2 GB the sessions hold
  after loading (the feature extractor drops 905 -> 439 MB, the decoder 308 -> 156 MB), but it changes the samples
  (max abs diff 4.5e-5, 100 dB SNR) and costs ~9-15 % CPU: rejected; basic and extended keep the duplicated weights.
* **`_side_db` and the channel copies.** The old code built float64 mid, side and their squares for the whole file and
  copied each channel (and the mid signal) up front. `_side_db` now works in blocks of 2^20 samples, channels are views of
  the (memory-mapped) input, and the mid signal is computed per requested slice. 30 min stereo (memmap): 1,978 MB -> 56 MB
  over the baseline for `_side_db` (the old code scales linearly: 90 min ~6 GB); the 1 GB-per-channel copies at 90 min
  and the temporary for the result are gone too.

## 4. AP-BWE

`CONTEXT` 4000 -> 2560 (the receptive field is ~2.4 k samples), `BLOCK_SECONDS` 3 -> 6, `allow_spinning=0`. 24 s of 8 kHz-class
speech, 1 thread: 0.843 / 0.845 -> 0.835 / 0.831 cpu-s/s, output identical to the old code (max abs diff 0). The measured
saving is 1 % here, not the audit's 7 %; the cost is +0.15 GB peak RSS from the longer blocks. Kept because it is free
in accuracy; the arena was not touched.

## 5. DeepFilterNet per thread

Not changed. libDF has no way to reset an instance (`df_*` exports: create, process, free, set_atten_lim, ...), so reusing
one across segments would start the next segment with the previous segment's recurrent state: the output would depend on
which thread got which segment, and differ from today's by more than the warm-up tolerance the code relies on. What a
create costs: 0.12 s CPU with the library in production, 0.035 s with the shared-weights build (not yet deployed), per
60 s segment of ~3 s CPU: 4 % and 1 %. Adding a `df_reset` to `tract-0.23.patch` (it would call `DfTract::init`) would make
the reuse exact; that is a libDF rebuild and not worth a 1 % saving once the shared build is deployed.

## 6. DPDFNet-8 batching

Source: Ceva-IP/DPDFNet, code commit 9bd9844 (`onnx_model/`), weights `checkpoints/dpdfnet8_48khz_hr.pth` at HF commit dd6818d
(the same commit as the published ONNX in the lock). `tools/export_dpdfnet_batch.py` loads the checkpoint with the
upstream classes and exports with a dynamic batch dimension:
`spec (B,1,481,2)`, `state_in (B,90228)` -> `spec_e (B,1,481,2)`, `state_out (B,90228)`; the state of a row has the
same sections as the batch-1 state. The upstream code is not edited: four state-handling modules, the dual-path RNN stack and
the top-level forward are replaced by batch-aware versions at export time (the FIFO sections keep the layout of the tensor
they feed, and the RNN stack runs channel-last, which removed about a seventh of the run time that went into 4-D transposes).
The export checks itself against PyTorch and against the published ONNX (max abs diff 1e-7 at batch 1, 3, 8). The reshapes
with literal batch-1 shapes make graph surgery on the published file impossible, as the audit said, so the re-export is the
only way.

Per-call cost, one core, onnxruntime 1.31, `intra_op=1` (cpu-s per audio second): published file 0.725-0.73; batched file B=1
0.62-0.67, B=2 0.50, B=4 0.43, B=8 0.417, B=16 0.405, B=32 0.495. Gemm is at the core's peak (50 GFLOP/s) and the bidirectional
GRUs (45 % of the rest) at 30; no further gain is available per call. `MAX_BATCH` is 8.

End to end (`denoise_array`, 485 s real speech, mono, 2 threads on 2 cores): published file 0.761 -> 0.512 cpu-s/s and wall
0.392 -> 0.284 s/s in a quiet run; 0.998 -> 0.620 and 0.506 -> 0.394 in a run that shared the cores with another job.
Output: max abs diff **0** between the two models on the same segmentation, also at `atten_lim_db` 12 and with 4 threads on
120 s. The audit's estimate of 1.5-2.5x applies to the call; the end-to-end figure is 1.5-1.6x because the first and last
segments of each thread and the warm-up (2 s per 60 s segment) are not batched, and a thread only batches the segments
that it has.

Design points:
* Segmentation is exactly the old one (`segment_seconds`, `overlap_seconds`, threads), independent of the model file: any
  other segmentation changes the output by 20-26 dB SNR against a sequential pass (the recurrent state after 2 s of
  warm-up is not the continuous state; this is true of the old code too: sequential vs 4 segments of 30 s = 26 dB), so
  shorter segments to batch short files were not used. Batching therefore helps files with more segments than threads:
  with 4 threads, 60 s segments and a single channel from ~4 min of audio.
* The segments of a call run in lock step, in groups of similar length, split evenly over the threads.
* A segment now processes only what it needs after its end (crossfade + the model's look-ahead, 150 ms) instead of 2 s of
  real audio: identical output, 3 % less work.
* `dpdfnet8_48khz_hr_batch.onnx` is used when it sits next to the standard file; `ACW_DPDFNET_BATCH=0` forces the old
  file. Both stay in `models/dpdfnet`; the standard file remains the required one (health check, desktop bundle).
  Lock entry: `local optional`, sha256 b50417b0..., 14,777,093 bytes. It cannot be fetched yet: publish it (for example in the
  next models archive as `dpdfnet/dpdfnet8_48khz_hr_batch.onnx` and turn the line into a `member`), then drop the batch-1
  file once the batch file is the default everywhere. The desktop installer still bundles only the old file and so keeps the
  old speed.
* Memory: a heavy stereo clean peaks at 0.23 GB private (0.82 GB with the mapped scratch files) over 485 s with 4 threads.
  `JOB_MEM` 1.5 GB -> 1.0 GB (band extension adds ~0.45 GB).

## 7. Whisper large-v3-turbo, BatchedInferencePipeline

The audit saw Turkish WER 16.3 % instead of 34.6 % with `BatchedInferencePipeline(batch_size=8)` on one clip. Checked on six
languages that production routes to Whisper (tr ar ja zh ko hi), FLEURS, 2-4 groups of 6 consecutive clips per language
(~80-110 s each, 18 paired groups, 11 groups of them new), large-v3-turbo int8, 1 thread, production settings (beam 5, word
timestamps, VAD filter, no conditioning on previous text) against the batched pipeline with the same options. Error is WER,
CER for ja and zh:

| language | groups | error, production | error, batched | batched better / worse |
|---|---|---|---|---|
| tr | 3 | 32.1 % | 27.6 % | 1 / 2 (16.3 vs 34.6, 22.1 vs 19.3, 44.2 vs 42.3) |
| ar | 3 | 15.3 % | 14.1 % | 2 / 1 |
| ja | 2 | 18.6 % | 10.2 % | 2 / 0 |
| ko | 3 | 18.3 % | 11.7 % | 3 / 0 |
| zh | 4 | 9.4 % | 13.3 % | 0 / 3 (14.8 vs 28.4 in one group, the batched output lost 24 words) |
| hi | 3 | 30.8 % | 38.9 % | 1 / 2 (16.0 vs 39.5 in one group: 50 words fewer) |
| all | 18 | 20.3 % (mean of groups) | 19.5 % | 9 / 8 |

Not consistently better or equal: it fixes the Turkish, Japanese and Korean cases the audit and this run found and
drops text elsewhere (Chinese, Hindi), so the quality lead is real in both directions. CPU is not lower either: 2.03 cpu-s
per audio second for production and 2.25 for batched on the five languages without Hindi (batched +11 %; Hindi
production runs 7.1 against 3.3 because it repeats decoding on some windows, which is an effect of its own). The
conclusion stays what the audit said: `transcribe.transcribe` is unchanged. The failure on the production path (text
dropped after a window the model decodes with timestamps) is worth a separate look if Turkish or Korean accuracy matters:
the cause is in the sequential timestamp-seek logic, not in the model. Numbers vary +-10 % with the load on the shared
cores (these runs shared two cores with other work; error rates are not affected by that).

## Not done / open

* DFN once per thread (5). A libDF `df_reset` would make it exact; worth ~1 %.
* The batched DPDFNet file is not in a published archive; until it is, only this box (and anything that builds it) has it.
* Short files do not profit from DPDFNet batching (fewer segments than threads); a segmentation change would alter the output.
* No real music for the language-detection test; a recording set with music beds would be a better check.
